# SEO Architecture

This document describes every SEO surface on the site: where each piece lives,
why it is built the way it is, and what to change when the site grows.

## Overview

All SEO output is generated by Next's Metadata API rather than hand-written
`<head>` tags. Nothing is duplicated into raw markup — if a tag needs to change,
it changes in exactly one of the files below.

```
src/lib/site.ts               ← single source of truth for the domain
├── src/app/robots.ts         → /robots.txt
├── src/app/sitemap.ts        → /sitemap.xml
├── src/app/opengraph-image.tsx → /opengraph-image  (1200×630 PNG)
└── src/app/layout.tsx        → site-wide defaults + Person JSON-LD
    ├── about/layout.tsx      → /about metadata
    ├── projects/layout.tsx   → /projects metadata
    ├── contact/page.tsx      → /contact metadata + FAQPage JSON-LD
    └── case/[slug]/page.tsx  → per-project metadata (generateMetadata)
```

## The canonical origin

`src/lib/site.ts` exports `SITE_URL` (`https://shaulakelo.com`), plus
`SITE_NAME` and `SITE_DESCRIPTION`. Every absolute URL Google sees — canonicals,
Open Graph tags, sitemap entries, JSON-LD — is derived from it.

It is a **plain constant, not an env var**, on purpose. The canonical host must
be byte-identical in every environment; if preview deploys emitted canonicals
pointing at their own `*.vercel.app` hostname, they would compete with
production in the index and split its ranking signals.

To move the site to a new domain, change this one value.

## Google Search Console verification

`public/googleedcc4cbe49e1037a.html` is Google's HTML verification file, served
at `https://shaulakelo.com/googleedcc4cbe49e1037a.html`.

It **must live in `public/`**. Next only serves static files from that
directory; a verification file in the repo root is not routed and returns 404,
which fails verification silently.

> Note: Search Console issues a *different* token for the meta-tag method than
> for the file method. If you ever switch to `metadata.verification.google`, get
> a fresh token from Search Console — the string in the filename is not it.

## Site-wide defaults (`src/app/layout.tsx`)

| Field | Value / behaviour |
| --- | --- |
| `metadataBase` | `new URL(SITE_URL)`. Required — relative URLs in any URL-based metadata field are a **build error** without it. |
| `title.default` | `Shaul Akelo — Web, 3D & Animation Developer` (used by `/` only) |
| `title.template` | `%s — Shaul Akelo`, so a child setting `title: 'About'` renders `About — Shaul Akelo` |
| `description` | `SITE_DESCRIPTION` |
| `alternates.canonical` | `/` |
| `openGraph` / `twitter` | Site-wide defaults; `twitter.card` is `summary_large_image` |
| `icons` | The animated `/shaul.gif` favicon — see the comment in the file before touching it |

### Inheritance caveat

`alternates.canonical: '/'` is inherited by any child segment that does not set
its own. **Every route currently overrides it.** If you add a route, it must set
its own canonical or it will declare itself a duplicate of the home page and
drop out of the index.

### `Person` JSON-LD

The root layout injects a `Person` schema on every page. This is what earns a
search for *"Shaul Akelo"* a single consolidated result instead of four
competing page listings — it tells Google the site and the person are one
entity.

`sameAs` is the array that links off-site profiles to this domain, and is the
strongest signal in the block. It currently holds only the GitHub profile;
**add LinkedIn, Behance, Dribbble, and any other profile as they exist.**

## Per-route metadata

Each route has a unique title, description, and canonical. This matters: before
this work every page inherited one title and one description, and Google treats
sitewide-identical metadata as duplicate content and writes its own snippets.

### Why `/about` and `/projects` use a `layout.tsx`

Both pages are `'use client'` components (the animated Hero, and the tab state
respectively), and **a client component cannot export `metadata`**. Each has a
thin server `layout.tsx` that carries the metadata and returns `children`
untouched.

If either page is ever converted to a server component, its metadata can move
inline and the layout can be deleted. `/contact` is already a server component,
so its metadata sits directly in `page.tsx`.

### Case studies (`case/[slug]/page.tsx`)

`generateMetadata` builds everything from the project record in
`src/data/projects.ts`: title, description, `keywords` from `tags`, canonical,
and OG/Twitter images from `project.image` (falling back to the app-level OG
image when a project has no artwork).

An unknown slug returns `robots: { index: false, follow: false }` so the 404
does not get indexed under the site-wide title.

### FAQ structured data

`/contact` emits a `FAQPage` schema built from the **same `faqs` array** that
the `FAQ` component renders. Deriving both from one source is deliberate: Google
discounts — and can penalise — FAQ markup describing content not visible on the
page, so the two can never drift apart.

## robots.txt

Allows everything except `/api/`, which holds only the quote-form POST handler
and has nothing crawlable. Declares `Host` and points at the sitemap.

## sitemap.xml

Static routes are listed explicitly with hand-tuned priorities (home `1.0`,
projects `0.9`, case studies `0.8`, about/contact `0.7`).

Case-study URLs are **derived from `uiuxProjects`** — the same array that drives
`generateStaticParams` — so uncommenting a project in `src/data/projects.ts`
adds its case study to the sitemap automatically. Only `pizza-app` is currently
active; the other project entries are commented out in the data file.

`lastModified` is a single timestamp captured once per build, not a per-request
`new Date()`. A timestamp that changes on every fetch makes every URL look
freshly edited every time, which trains Google to ignore the field.

## Open Graph image

`src/app/opengraph-image.tsx` generates a 1200×630 PNG at build time using
`ImageResponse` from `next/og`, so there is no binary asset to keep in sync with
the site's wording.

It uses no custom fonts deliberately — loading one requires fetching and passing
the font buffer, and the default face is adequate for three lines of text. Case
studies override this with real project artwork.

## Verifying changes

`npm run build` is the check. The route table must list `/robots.txt`,
`/sitemap.xml`, and `/opengraph-image`, and the generated output can be read
directly:

```bash
cat .next/server/app/robots.txt.body
cat .next/server/app/sitemap.xml.body

# unique title + canonical per route
grep -o '<title>[^<]*</title>' .next/server/app/about.html
```

When counting JSON-LD blocks in built HTML, match the full opening tag
(`'<script type="application/ld+json"'`). Grepping for `application/ld+json`
alone double-counts, because the string also appears inside the serialised RSC
payload embedded in the page.

## What this does not do

Technical SEO makes the site **eligible** to rank; it does not rank it. The
remaining work is off-page and editorial:

- **Written content.** Case studies need substantive indexable prose. Text baked
  into images is invisible to Google. One live case study (`pizza-app`) is thin
  ground to rank on — the commented-out projects are the biggest available win.
- **Backlinks.** Get the domain onto the GitHub profile, LinkedIn, and any
  directory listing. These also reinforce the `sameAs` entity signal above.
- **Client-side rendering.** Most pages are `'use client'` with a
  `PageTransition` wrapper. Google does render JavaScript, but server-rendered
  text is strictly safer — worth confirming with Search Console's URL Inspection
  tool ("view crawled page") that body copy appears in the crawled HTML.
- **Search Console.** Submit `https://shaulakelo.com/sitemap.xml` after
  verification completes.
